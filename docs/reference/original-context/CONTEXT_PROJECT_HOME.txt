=============================================================================== 1.
PROJECT PURPOSE
===============================================================================

This project is a serious personal DevOps/Platform Engineering
laboratory built around the real home environment.

The objective is NOT simply to make a home server work.

The objective is to design, implement, operate, monitor, secure,
version, upgrade, break, recover and document a small production-grade
platform using real engineering practices.

The physical infrastructure is homelab-sized, but the engineering
processes should intentionally resemble those used in professional
companies.

Core principle:

    "Production-grade practices, adapted to homelab scale."

Do not simplify professional engineering practices merely because this
is a home environment. Simplify only where additional complexity does
not provide meaningful reliability, security, operational or learning
value.

This project is also a long-term practical training environment for a
junior DevOps engineer. The architecture should therefore deliberately
expose the owner to real concepts such as:

-   Git and release management
-   Infrastructure as Code
-   Configuration management
-   CI/CD
-   GitOps
-   Kubernetes
-   progressive delivery
-   Blue/Green deployments
-   observability

-   network segmentation

-   backup and disaster recovery

2. DESIGN PHILOSOPHY
===============================================================================

The project must be:

1.  Versioned
2.  Reproducible
3.  Automated
4.  Observable
5.  Secure
6.  Redundant where justified
7.  Recoverable
8.  Testable
9.  Documented
10. Maintainable
11. Simple enough to operate correctly
12. Designed before implementation

For every stateful service, the required outcome is not merely that its
container starts. It must retain its state across a pod/container restart,
host reboot, upgrade and, after a tested restore, total host loss.

Avoid:

-   manual configuration that should be code
-   hidden state
-   undocumented infrastructure
-   unpinned production dependencies
-   secrets in Git
-   unnecessary public exposure
-   Kubernetes being responsible for critical network routing
-   unnecessary abstractions
-   introducing technology only because it is fashionable
-   overengineering without a measurable benefit

Important principle:

    Inspect -> Design -> Review -> Implement -> Test -> Document

Never blindly change critical infrastructure.

4.1 INITIAL HARDWARE DEPLOYMENT MODEL
===============================================================================

This is the approved target direction for Phase 0 planning, not a statement
that the hardware has been purchased or deployed. The owner currently has no
dedicated homelab hardware; the work computer must not become a permanently
required home-infrastructure host.

The platform separates three failure and security domains:

    router/firewall  !=  application server  !=  backup/storage system

1. Dedicated router/firewall: terminates the Internet connection and owns
   routing, DHCP, VLANs, firewall policy and private WireGuard access. It
   must remain independent of Kubernetes. Target class: a dedicated x86-64
   appliance with sufficient ports for WAN/LAN expansion, reliable NICs,
   approximately 8 GB RAM and SSD storage; exact model depends on ISP,
   fibre/voice requirements and measured bandwidth.

2. Dedicated application server: a wired x86-64 business SFF workstation or
   similarly expandable host, running Ubuntu and the initial single-node
   Kubernetes platform. Planning baseline: 32 GB RAM and 1 TB NVMe SSD, with
   capacity to expand. It hosts GitOps, observability, Home Assistant, MQTT
   and approved future workloads. A single node is not HA; backups and tested
   recovery are mandatory until redundancy is deliberately introduced.

3. Dedicated NAS/backup system: primarily stores backups, shared files and
   future media. Planning baseline: two bays with two equal CMR disks in a
   mirror. It is not the initial Kubernetes application server. Mirroring
   protects against a disk failure but does not replace local and off-site
   backups.

4. Managed network switch: supports IEEE 802.1Q VLANs, with enough ports for
   firewall, server, NAS and wired APs. PoE is required only if chosen APs or
   cameras need it.

5. UPS: protects the router/firewall, switch, server and NAS from short power
   loss and enables orderly shutdown where supported.

Initial storage rule: live stateful workloads use deliberate persistent
storage on the application server; the NAS receives automated backups. This
avoids making a NAS outage an immediate outage of every application. Future
storage/HA changes require a separately reviewed design.

Recommended acquisition order:

    1. Confirm ISP/ONT/router constraints and choose router/firewall
    2. Managed switch
    3. Application server
    4. NAS and CMR disks
    5. UPS
    6. Wired APs and later IoT/camera hardware

Do not buy camera accelerators, large recording storage, multiple Kubernetes
nodes or advanced HA components until workload, camera retention, budget,
noise, power and Ethernet availability have been inventoried.

7. CURRENT SMART VIEW / CASTING PROBLEM
===============================================================================

Samsung Smart View mirroring to an old LG TV or Amazon Fire TV is
unstable after several minutes.

The same phone and equipment worked correctly in a previous apartment.

In the current house, disabling the two repeaters often makes mirroring
work correctly while the main router remains operational.

Current working hypothesis:

    Repeater topology / wireless backhaul may be interfering with
    multicast/discovery/bridging behavior required by Smart View/Miracast or
    casting.

This is a hypothesis, not a proven root cause.

Important distinction:

Streaming: Internet/server -> mobile

Mirroring: mobile -> local TV/Fire TV

Server saturation should not normally directly terminate local
mirroring, although traffic/load may be a trigger.

Long-term preferred network architecture:

-   one stable LAN
-   properly managed APs
-   preferably Ethernet backhaul
-   controlled multicast/discovery behavior
-   VLAN-aware design where required
-   no unnecessary wireless repeater chains

When implementing VLANs, explicitly account for mDNS/SSDP/casting/Home
Assistant/IoT discovery requirements.

9. VPN ARCHITECTURE
===============================================================================

There are two completely separate VPN use cases.

9.1 PRIVATE REMOTE ACCESS - WIREGUARD

Purpose:

Securely access home resources from outside the house.

Potential resources:

-   security cameras
-   smart plugs
-   heating/thermostats
-   exterior lighting
-   Home Assistant
-   Ubuntu
-   Kubernetes services
-   Grafana
-   storage
-   media
-   files
-   other home services

Preferred architecture:

    Internet
       |
    WireGuard
       |
    Firewall
       |
    HOME / SERVERS / IOT

Each trusted device should have its own cryptographic identity/key.

Do not use one shared VPN credential for everyone.

Prefer per-peer access control.

Example:

Owner: HOME + SERVERS + selected IOT

Family member: only explicitly required resources

Do not expose SSH, Grafana, cameras, Kubernetes, Home Assistant or other
management services directly to the Internet unless there is a
documented, deliberate reason.

9.2 OUTBOUND INTERNET VPN - EXPRESSVPN

Purpose:

Allow selected physical devices to route Internet traffic through
ExpressVPN.

This is NOT the same as WireGuard remote access.

Desired behavior:

    Selected device
        |
    policy routing
        |
    ExpressVPN
        |
    Internet

Other devices:

    device
       |
    normal Internet

Local LAN traffic should remain local and should not unnecessarily
traverse the outbound VPN.

Possible implementations: - router/firewall VPN client with policy
routing - dedicated Linux gateway - other deliberately designed routing
solution

Do not assume the current Sagemcom supports ExpressVPN client mode until
verified.

Do not make Kubernetes the critical home router unless there is a strong
architectural reason.

14. REDUNDANCY / HIGH AVAILABILITY
===============================================================================

The final architecture should be intentionally redundant where
justified.

Target principles:

-   avoid unnecessary single points of failure
-   use multiple replicas for appropriate stateless workloads
-   use pod anti-affinity/topology spread where meaningful
-   design DNS for availability
-   design monitoring for availability
-   maintain storage resilience and backups
-   make remote access recoverable
-   make infrastructure reproducible

Important:

    Redundancy != backup

    3 replicas + no backup is not a disaster recovery strategy.

The project should distinguish:

-   high availability
-   replication
-   redundancy
-   backup
-   restore
-   disaster recovery

For Kubernetes, eventually practice: - pod failure - node failure -
deployment failure - rescheduling - rolling updates - controlled node
drain

If hardware allows a multi-node cluster, the design should support it.
If physical hardware is initially limited, the architecture and
manifests should still follow production principles where practical
without pretending single-node infrastructure is truly HA.

24.1 STATE OWNERSHIP, PERSISTENCE AND FULL RECOVERY
===============================================================================

GitOps describes the desired platform state; it is not a substitute for
application data. Every deployed component must classify its state and have
an explicit owner and recovery path:

1. Declarative configuration: Argo CD Applications, Helm chart versions,
   Helm values, Kustomize overlays, dashboards, alerts, policies, and
   infrastructure configuration. These belong in Git and must be versioned.

2. Secrets and cryptographic identity: API tokens, passwords, TLS material,
   WireGuard peer keys, MQTT credentials and encryption keys. These must
   never be stored in plaintext in Git. They require encrypted secret
   management and a separately protected recovery copy of the decryption
   material.

3. Persistent application state: databases, application configuration,
   paired device state, automations, integrations and recordings. This must
   be stored on durable storage outside a container filesystem (for example
   Kubernetes PVCs backed by a deliberate storage solution) and backed up.

4. External network-device configuration: router, firewall, switch and AP
   configuration. This is outside Kubernetes and must have a documented,
   secure export/backup and restore procedure where the device supports it.

Container filesystems and Kubernetes ephemeral volumes must never be the
only location for data that is needed after restart or recovery. A chart
deployment must explicitly enable and configure persistence before the
service is accepted.

Home-critical services require service-specific recovery guarantees:

- Home Assistant: configuration, database, integrations, automations,
  dashboards and paired-device state must be recoverable without re-adding
  devices wherever the integration permits it.
- MQTT: configuration, users, ACLs, certificates and required persistence
  must be recoverable.
- AdGuard Home/DNS: configuration, filters, local records, rewrites and
  client policy must be recoverable.
- Cameras/NVR: configuration, credentials, retention policy and metadata
  must be recoverable; recording retention and backup scope are an explicit
  capacity decision.
- Zigbee/Z-Wave/Thread: coordinator and network backup material must be
  identified, protected and restore-tested before relying on the network.

The recovery target for a total host failure is:

    replacement host
       -> automated host/bootstrap configuration
       -> Kubernetes and Argo CD
       -> GitOps redeploy
       -> restore persistent data and secrets
       -> functional verification of home services

The desired result is a functioning home, not an empty set of freshly
started containers. Backups are not valid until their restore procedure has
been exercised and documented.

32. MASTER IMPLEMENTATION ROADMAP
===============================================================================

The project must be designed globally before implementation starts.

Progress tracking convention: mark a phase `[x]` only when its exit
criteria, documentation and evidence are complete. A partial implementation
remains `[ ]`; record its current state and open work in ROADMAP.md.

- [ ] PHASE 0 - ARCHITECTURE, STANDARDS AND RECOVERY DESIGN
  - Define repository structure, Git strategy, environments, naming,
    versioning, dependency/update policy and ADR process.
  - Define the application-selection policy: prefer maintained community
    software and official charts/operators; do not fork or copy upstream
    applications unless a concrete modification is required.
  - Define the GitOps model: Git stores deployment declarations and owned
    configuration; Helm/Kustomize deploy pinned upstream artifacts.
  - Define state ownership, persistent-storage, secrets and full-recovery
    requirements before selecting home-critical services.
  - Exit: approved architecture, initial ADRs, service inventory template,
    backup/restore matrix and no disruptive infrastructure changes.

- [ ] PHASE 1 - INVENTORY / HOST BASELINE
  - Inspect Ubuntu, CPU, RAM, disks, SMART/temperatures, network interfaces,
    Ethernet, Wi-Fi, routing, DNS, firewall, SSH, runtime and virtualization.
  - Exit: factual inventory, documented gaps/blockers and reviewed plan.

- [ ] PHASE 2 - PHYSICAL NETWORK / FIREWALL DESIGN
  - Verify Ethernet and repeater/AP topology; evaluate router/firewall
    capabilities; design VLANs, firewall and multicast/discovery behaviour.
  - Diagnose or isolate the Smart View/casting issue.
  - Exit: reviewed network design and rollback plan. No critical network
    change is made without explicit approval.

- [ ] PHASE 3 - HOST, STORAGE AND BACKUP FOUNDATION
  - Configure Ubuntu hardening, SSH, packages, filesystem/storage, Ansible,
    host monitoring and backup destinations.
  - Establish durable storage outside container filesystems and test a basic
    host/data restore.
  - Exit: automated host baseline and verified persistent-storage path.

- [ ] PHASE 4 - KUBERNETES PLATFORM
  - Implement Kubernetes, CNI, durable storage, ingress, namespaces,
    resource policies, probes and baseline NetworkPolicies.
  - Exit: a workload with a PVC survives pod recreation and host-recovery
    procedures are documented.

- [ ] PHASE 5 - GITOPS AND APPLICATION LIFECYCLE
  - Configure GitHub Actions, Argo CD, projects/applications, sync policies,
    drift detection and deployment conventions.
  - Pin chart and image versions; use Helm values/Kustomize for local needs.
  - Exit: a sample upstream application is reproducibly deployed from Git
    without manually applying its normal state with kubectl.

- [ ] PHASE 6 - PROGRESSIVE DELIVERY
  - Add Argo Rollouts Blue/Green only where operationally useful, with smoke
    tests, health checks, promotion, rollback and optional analysis.
  - Exit: a controlled bad-release and rollback exercise is evidenced.

- [ ] PHASE 7 - OBSERVABILITY
  - Deploy Prometheus, Grafana, Loki, Alertmanager and required exporters;
    create dashboards, actionable alerts and initial meaningful SLI/SLOs.
  - Exit: deliberate service and host failures are detected and diagnosed.

- [ ] PHASE 8 - SECURITY
  - Implement RBAC, NetworkPolicies, encrypted secrets, TLS, image and
    dependency scanning, audit and security monitoring.
  - Exit: secrets are absent from plaintext Git and access is least-privilege.

- [ ] PHASE 9 - DNS / NETWORK SERVICES
  - Deploy AdGuard Home with persistent configuration, local DNS,
    redundancy/fallback, VPN DNS integration and monitoring.
  - Exit: DNS configuration and its restore have been tested.

- [ ] PHASE 10 - PRIVATE REMOTE ACCESS
  - Deploy WireGuard with individual peers, access policy, firewall rules,
    remote DNS, monitoring and recovery of peer identity.
  - Exit: remote access is tested without exposing management services.

- [ ] PHASE 11 - OUTBOUND VPN
  - Implement ExpressVPN policy routing for selected devices, local-traffic
    bypass, failure behaviour and monitoring.
  - Exit: policy and fail-safe behaviour are tested and documented.

- [ ] PHASE 12 - SERVICE BACKUPS AND RECOVERY
  - Implement per-service backups, retention, encryption, off-site copy and
    restoration testing for application data, secrets and network devices.
  - Exit: the backup/restore matrix has evidence for every critical service.

- [ ] PHASE 13 - HOME AUTOMATION
  - Deploy persistent Home Assistant and MQTT, then onboard devices,
    sensors, lights, plugs, heating and automations.
  - Protect coordinator/network backups and prove that a restore does not
    require manually re-pairing supported devices.
  - Exit: Home Assistant/MQTT restore is functionally verified.

- [ ] PHASE 14 - CAMERAS / NVR
  - Implement camera segmentation, NVR, durable recording storage, retention,
    alerts and WireGuard-only remote access.
  - Exit: NVR configuration and the agreed recording-recovery scope are tested.

- [ ] PHASE 15 - MEDIA / PERSONAL SERVICES
  - Add Jellyfin, Syncthing, file services and further approved services with
    explicit persistence, backup, monitoring and security decisions.
  - Exit: each service meets the Definition of Done below.

- [ ] PHASE 16 - RELIABILITY / HA
  - Add justified replicas, disruption budgets, topology spread and failure
    tests for nodes, services and dependencies.
  - Exit: resilience claims are supported by documented exercises.

- [ ] PHASE 17 - INCIDENT MANAGEMENT
  - Establish alerts, runbooks, incident templates, postmortems and
    operational procedures.
  - Exit: at least one realistic incident is handled end-to-end.

- [ ] PHASE 18 - DISASTER RECOVERY EXERCISE
  - Rebuild from a clean/replacement host: bootstrap, IaC, Kubernetes,
    Argo CD, GitOps redeploy, data/secret restore and functional verification.
  - Exit: the recovery time/result is recorded and corrective actions closed.

- [ ] PHASE 19 - CONTINUOUS IMPROVEMENT
  - Perform controlled dependency/platform/security upgrades and improve
    performance, capacity, cost, architecture and documentation.
  - Exit: ongoing, reviewed at each release; this phase is not permanently
    marked complete.

===============================================================================
33. DEFINITION OF DONE
===============================================================================

A component is not considered complete merely because it runs.

Where applicable, completion means:

-   code/configuration is versioned
-   dependencies are pinned/locked
-   deployment is automated
-   secrets are managed securely
-   health checks exist
-   monitoring exists
-   logs are available
-   alerts exist where useful
-   backup strategy is defined
-   persistent state is stored outside the container/ephemeral volume
-   backup scope includes configuration, data and required identities
-   a restore has been tested with documented evidence
-   recovery behavior is understood
-   security controls are applied
-   documentation exists
-   failure mode is known
-   rollback strategy exists
-   CI validation passes
-   GitOps reconciliation works
-   manual steps are minimized and documented

For home-critical services, the Definition of Done additionally requires
that a replacement-host recovery restores the service's useful state rather
than presenting an empty, newly installed application.

34. FINAL ARCHITECTURAL PRINCIPLE
===============================================================================

This project should behave like a small internal platform owned by an
engineering team of one.

The goal is not to imitate enterprise complexity.

The goal is to practice enterprise-quality engineering discipline:

-   design before implementation
-   source control
-   reproducibility
-   automation
-   least privilege
-   immutable deployments
-   progressive delivery
-   observability
-   reliability
-   change management
-   incident response
-   disaster recovery
-   continuous improvement

The system should be capable of answering:

    What is running?
    Why is it running?
    Which version is running?
    Who changed it?
    When was it changed?
    Can we detect when it breaks?
    Can we roll it back?
    Can we recover it?
    Can we rebuild it?
    Can we prove that it is secure?
    Can we upgrade it safely?

If the answer to those questions is consistently “yes”, the project is
achieving its intended purpose.
